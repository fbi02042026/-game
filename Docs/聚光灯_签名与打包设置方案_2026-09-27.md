## 1. 正式 keystore（聚光灯参赛包用）

### 1.1 为什么要正式签名

- 现在 `PlayerSettings` 里 `androidUseCustomKeystore: 0`、`AndroidKeystoreName:` 为空 → 打出来的是 **debug 签名**。
- debug 签名的问题：**装过 debug 包之后，再装签名不同的正式包会装不上**（提示"签名不一致/需卸载"）。比赛要反复传包给 TapTap 检测，用同一个正式签名最省事。
- ⚠ 另一条更硬的理由：**签名一旦定下就不能换**。换了签名 = 老用户全部升级失败。所以现在定下正式 keystore，比以后换要划算得多。

**结论：聚光灯这一次就定下正式 keystore，用一辈子。**

### 1.2 签名文件长什么样（要主人亲手做）

keystore 本质是一个 `.jks` 文件 + 三个密码/名字：

| 项 | 说明 | 建议值 |
|---|---|---|
| 文件 | 证书仓库文件 | `E:\xiangsumaoxian\Keys\pixeladventure-release.jks` |
| store password | 仓库密码 | 主人自定（**别告诉我，别提交到 git**） |
| key alias | 别名 | `pixeladventure` |
| key password | 别名密码 | 建议与 store password 相同（Unity 默认用同一个） |
| validity | 有效期 | **10000 天**（≈27 年，TapTap 要求 ≥ 25 年 保险） |
| dname | 证书主体 | CN=PixelAdventure, OU=Games, O=PixelAdventure, L=Beijing, ST=Beijing, C=CN |
| keyalg / keysize | 算法强度 | RSA / 2048（若工具支持选 `RSA 4096` 更好） |

### 1.3 怎么生成 —— 二选一

**方式 A：用命令生成（推荐，参数可控）**

本机有现成 keytool（团结自带 JDK，不用另外装）：

```
E:\Program Files\Tuanjie\Hub\Editor\2022.3.62t12\Editor\Data\PlaybackEngines\AndroidPlayer\OpenJDK\bin\keytool.exe
```

在项目根目录 `E:\xiangsumaoxian` 新建 `Keys` 文件夹，然后在**普通命令行窗口**里跑（会交互问密码，所以不要让我代跑）：

```
mkdir E:\xiangsumaoxian\Keys
cd E:\xiangsumaoxian\Keys
"E:\Program Files\Tuanjie\Hub\Editor\2022.3.62t12\Editor\Data\PlaybackEngines\AndroidPlayer\OpenJDK\bin\keytool.exe" -genkeypair -v ^
  -keystore pixeladventure-release.jks ^
  -alias pixeladventure ^
  -keyalg RSA -keysize 4096 -validity 10000 ^
  -dname "CN=PixelAdventure, OU=Games, O=PixelAdventure, L=Beijing, ST=Beijing, C=CN"
```

会依次问：
- `Enter keystore password:` → 输入并记住
- `Re-enter new password:` → 再输一次
- （若 JDK 支持且选了 PKCS12，不会再单独问 key password）

生成成功后 `Keys\` 下就有 `pixeladventure-release.jks`。

### 1.5 交付物（TapTap 上架/软著要）

生成 keystore 后，用同目录下的 keytool 导出证书指纹（TapTap DC 建游戏页会要）：

```

```

把 **MD5 / SHA1 / SHA256** 三行抄进 `Docs/聚光灯_TapPlay上架清单.md` 或另存一份记录文件。

### 1.6 安全红线（必须做）

1. **`.jks` 文件绝不提交 git.** 现在 `.gitignore` 里没有这条，麻烦主人确认一下；如果要女仆加，说一声（加 `.gitignore` 是安全动作，不涉及业务逻辑）。
2. **密码不要写进任何会被提交的文件**（包括 `.bat`、`.md`、任何 `.cs`）。
3. keystore + 密码**单独备份到一个不在这台电脑的地方**（网盘/U 盘/密码管理器）。丢了 = 以后没法更新这个游戏。
4. `Keys/` 整个目录建议进 `.gitignore`。

### 1.7 为什么现在 `useCustomKeystore` 我建议本轮先不代勾

勾上 Custom Keystore 之后，**如果密码填错，打包会直接失败**；而现在主人的手动 GUI 打包还没验证成功过一次。所以顺序建议：

1. 先用现在的 debug 签名，**手动 GUI 打一次包，确认流程能走通**；
2. 再回来填 keystore，**再打一次包**确认签名生效。

两步分开，出问题才好定位。

### 5.2 本轮明确不做的事

- ❌ 不启用 `ContentProtection`
- ❌ 不跑 `Tools/Data/Cook Tables (加密)`（明文档保持）
- ❌ 不启用团结的**引擎资源加密 / AssetBundle 加密**（上次坏预制体的就是这个）
- ❌ 不打 AssetBundle 分包（见 5.3）
- ❌ 不装回 Codely（`cn.tuanjie.codely.bridge`）

### 5.3 关于「是否要打 bundle」的结论

**本轮不打。** 理由：

1. **当前 `Assets/` 里的预制体已经是打包进 APK 了**，不需要额外 bundle 就能跑起来 —— 打 bundle 是为了"热更"，而聚光灯规则**明令禁止 WebView 热更**（`Docs/聚光灯_TapPlay上架清单.md` 第 58 行）。
2. 聚光灯参赛包是**断网可玩**的，包体不追求小（APK 走 TapPlay 下载）。
3. **上次预制体被搞坏，就是资源加密/属性加密那一类链路**。bundle + 加密的组合正是最容易出这种事的，本轮完全避开。
4. 以后真要做热更再单独立项，届时按 `Docs/软著后开发备忘.md` 第 178 行的上线前检查清单走。

### 5.4 唯一"要加密"的合法选项（了解即可，本轮不做）

团结的 `Player → Publishing Settings → Build → Custom Gradle Template` + 代码混淆（ProGuard）是**另一个方向**，和资源加密无关。本轮也不开（`AndroidMinifyRelease = 0`）。
