## 〇、🔴 先搞清一件事：「是不是传奇」到底谁说了算（2026-10-09 实测）

| 环节 | 判定方式 | 位置 |
|---|---|---|
| 装备实例的品质 | `EquipInstance.rarity`，`Rarity` 枚举 **Common1 / Uncommon2 / Rare3 / Epic4 / Legendary5** | `EquipTemplate.cs:8-15` |
| **副本掉落**的品质 | `hidden_level_rules.csv` 三档权重摇号 → `MapToEngineRarity` 映射成 `Rarity`（实际只会出 1 / 3 / 5 三档） | `RiftEquipGenerator.cs:98-126`、`:316-324` |
| **抽奖**的品质 | 与掉落**完全同一条路**：`DraftPool.cs:419` → `ConfigManager.GetRandomEquipInstances` → **`RiftEquipGenerator.Generate`**（`ConfigManager.cs:154`） | **无保底**，比例就是 `hidden_level_rules` |
| 铁匠门槛 | 铁匠 < 2 级 **且** 普通关 → 传奇权重强制归 0 | `RiftEquipGenerator.cs:111-112` |
| 模板的 `baseRarity: 5` | **只在**异常回退 / 初始装 / 引导武器（走 `EquipInstance.GenerateFromTemplate`）时直接当实例品质；**掉落和抽奖都不看它** | `EquipInstance.cs:82` |

品质是**摇号摇出来的**。这就是「改模板 `baseAttr`」对掉落和抽奖**完全无效**的根因（见 T8-B）。

## 附：名词解释 —— 「死字段」到底是什么（主人 10-09 要求：以后提到都要带说明）

**死字段** = 代码里**声明了、甚至也从存档里序列化了，但没有任何游戏逻辑会往里写值、也没有任何逻辑读了它能产生效果**的字段。
也就是说：它占着位置、看着像功能，但**从头到尾没参与过任何一次实际运算**。

分两种：

| 类型 | 特征 | 为什么危险 |
|---|---|---|
| **纯死字段** | 只有一处声明，**没人读也没人写** | 容易被后来人误以为「这里有个开关」，改了半天发现毫无反应 |
| **空转机制** | 有人读、也有存档序列化，**但永远没人写入** → 读到的永远是空值 | 更隐蔽：代码看着完整、注释写着功能，实际那段逻辑一次都没跑过 |

### 本项目里现存的三处

| 字段 | 位置 | 类型 | 现状 |
|---|---|---|---|
| `EquipTemplate.isLegendary` | `EquipTemplate.cs:95` | **纯死字段** | `public bool isLegendary;` 只有这一处声明，全代码零读取。跟同一行上面的 `baseRarity`（品质枚举）功能重复。**16 件传奇模板上它仍然是 0，不影响任何东西。** |
| `SaveData.unlockedLegendaryWeapons` | `SaveData.cs:72`（存档镜像 `:71`） | **空转机制** | 有反序列化填充（`:385`）、有序列化（`:721-723`）、也有读取（`AttrSystem.cs:153`「传说武器永久全局加成」），但**全代码没有任何一处 `.Add()`** → 集合永远为空 → 那段加成逻辑永远不产生效果。 |
| `SaveData.legacyEquipPool` | `SaveData.cs:107` | **空转机制** | 「遗产装备 / 永久装备库存」。只有 UI 读取展示（`CharacterBagSystem.cs:81`、`TownBackpackGrid.cs:567`），**没有任何写入** → 当前游戏不存在永久装备。主人已定：**现在不做，以后改成「武器库 + 符石」，以后再说**。 |

> 处置原则（主人 10-09）：**死字段只报告、不自动清理**；以后每次提到死字段，都要写清
> 「是什么 / 在哪个文件哪一行 / 属于哪一种 / 现在影响不影响」。
