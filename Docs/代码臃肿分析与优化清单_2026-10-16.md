## 三、通用手法（先做这几件，见效最快）

### 手法 A：抽 UI 层级构建器（收益最大、风险最低）
全项目有 **19 个文件**重复写同一套 `BuildHierarchyForPrefab()`，逐个手写「建 Image / 加 LayoutElement / 设 anchor」。
→ 建 `UI/Kit/UiBuilder.cs`（`Img()` / `Txt()` / `Btn()` / `Anchor()` / `Stretch()` 静态小函数），
新界面一律用它；**旧文件不批量重写**，只在改到某个方法时顺手替换（守 $AGENTS.md$ §4「不误伤已有逻辑」的规矩）。
**验收**：新写弹窗代码行数降到原来的 1/3；旧界面视觉零变化。

### 手法 B：`partial` 纵向切片（改不动整体时的过渡）
对 `BattleManager`、`UnitBase` 这种被大量外部引用的上帝类，**先按职责切成 partial 文件**，类名和字段全不变，
外部调用零改动，编译行为零变化。
- `BattleManager.cs`（状态/生命周期）
- `BattleManager.Waves.cs`
- `BattleManager.Skills.cs`
- `BattleManager.Settlement.cs`
- `BattleManager.Stats.cs`
**验收**：拆完 `git diff --stat` 纯位移，编译无报错，跑一局战斗行为一致。
这一步本身不减总量，但把「在 4170 行里找位置」变成「在 400 行里找位置」，是后续真拆分的前置。

### 手法 C：提取真类（partial 之后再抽）
把 partial 里的纯函数（不写 this 字段、只吃参数）整块搬进 `Combat/` 或 `Systems/` 下的静态/实例类。
注意：**碰 `[SerializeField]` 字段或 prefab 挂载成分的，不能在 prefeab 里重新拖 —— 那种留 partial，别硬抽**。

### 手法 D：大表进配置
`Monster.Init()` 293 行、`TalentUI` 的 54 个字段、`WavePlanner` 的编成规则，本质都是**数据表被写成了代码**。
→ 挪进 `Config/` 下的 Defs 或 csv（按 `配表与数据.md` 口径），代码只留「读表 + 应用」。

## 五、施工红线

1. **分批做、一次验收一批**：每批只动一个文件，主人 Ctrl+R 编译 + 进游戏跑一遍再动下一个。
   禁止一次性改 10 个文件然后一起报，出问题没法二分。
2. **`[SerializeField]` / prefab 挂引用的成员不要硬挪类**：挪了 prefab 引用就断，要挪必须同时在 prefab 里重挂（按 `AGENTS.md` §4 不许为救断链兜底）。
3. **禁止顺手美化**：不动当前没问题的地方，不做风格统一，只做搬运。
4. **partial 拆分阶段必须是纯位移**：不允许在拆的同时改逻辑，否则 review 时看不出真实 diff。
5. `BattleUI.*.cs` 已经 8 个 partial 了，**不要再新增 `BattleUI.Xxx.cs`**（旧约定），新 UI 单独建文件。
6. 优化不改任何数值/行为，只改代码组织 —— 这条是所有「拆分/搬运类改动」的兜底验收标准。

## 六、建议执行顺序（ROI 从高到低）

1. **A 抽 UI 构建器**（19 个文件受益，后续所有新 UI 立刻省 2/3 代码）— 立即可做，风险最低
2. **B BattleManager partial 切片**（把最难改的文件先变得能读）— 纯位移，可放心做
3. **Monster.Init / SaveData 双向同步**（单方法级，改动封闭、易验收）
4. **AdventureUI / TalentUI 拆 View 子组件**（UI 独立性强，炸了也不影响战斗）
5. **UnitBase / BattleManager 的 region 抽真类**（最后做，等前面积累信心）
