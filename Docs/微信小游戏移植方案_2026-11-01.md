# 微信小游戏移植方案（2026-11-01，当日 15:30 主人拍板修订版）

> **拍板结论（2026-11-01）**：无内购（跳过支付线）、无后端无域名（不做微信登录，纯本地存档，资源托管走微信云开发免备案）、TapTap 端放弃（Android 包不再是约束，可大胆剥离 TapTap SDK）。
>
> 结论先行：**可行，且工程底子不错**——用的是团结引擎 1.10.4（内置微信小游戏构建目标，不用走社区转换方案），UI 是 720×1280 竖屏、URP 2D，天然适合小游戏。主要工作量在：**① 资源瘦身（引用分析已出：1.3GB 候选零引用）、② 音效转码、③ TapTap/AdMob 剥离换微信广告、④ 视频播放特殊处理**。

## 一、现状盘点（实测数据）

| 项 | 现状 | 对小游戏的影响 |
|---|---|---|
| 引擎 | 团结引擎 1.10.4（Unity 2022.3.62t16） | ✅ 原生支持微信小游戏构建，最大利好 |
| 渲染 | URP 14.2.0-t1 | ✅ 支持，注意粒子/Shader 兼容性 |
| Assets 总量 | **1.7GB**，其中 Art/Effects 占 **1.27GB** | 大部分应该是商店包整包导入，实际用到的远没这么多，需要引用分析后裁剪 |
| Resources | **253MB**（UI/Art 83MB、Icons 48MB、Audio 45MB、VFX 18MB、Story 16MB、Prefabs 9MB） | ⚠️ 全走 Resources.Load，无 Addressables，首包裁剪要动资源加载结构 |
| 音频 | 特效音效全是 WAV，单个 **4~8MB**（Pixel Craft VFX 那套 Loop 音效）；BGM mp3 5MB | 🔴 小游戏音频必须 mp3/ogg 且压码率，这块是最容易见效的瘦身点 |
| 视频 | StreamingAssets/opening_intro.mp4（15MB），3 处代码用 VideoPlayer | 🔴 微信 WebGL 环境 VideoPlayer 不能直接用，要换方案 |
| 平台 SDK | TapTap SDK（登录/评价）、DirichletMediation 广告聚合、External Dependency Manager（Android 专用） | 🔴 小游戏上全部不可用，要换成微信对应能力 |
| 存档 | PlayerPrefs + 文件（SaveSystem） | ✅ 适配层会自动映射到 wx 存储，基本不用改 |
| UI 适配 | 720×1280 竖屏 + UICanvasSetup/SafeAreaFitter 统一出口 | ✅ 小游戏跑在竖屏容器里，基本复用 |
| 依赖模块 | 带 VR/XR/Terrain/Vehicles 等无关模块 | WebGL 构建自动裁剪，不用管 |

**微信小游戏硬限制（方案设计的出发点）**：
- 主包（代码+首包资源）**4MB**；整包（含分包）**30MB**；超出部分走 CDN 动态下载（无上限）。
- 首次进游戏要过加载页：CDN 资源要配合loading界面分批拉。
- 所有网络请求域名必须**备案**并配到小游戏后台白名单（request/downloadFile 合法域名）。
- iOS 端内存比安卓紧，WebGL 内存堆建议控制在 400~500MB 以内。

## 二、代码改造点（TapTap 端已放弃，按小游戏单一平台做）

### 2.1 平台能力替换
- **登录：整个砍掉**。无内购无排行，`wx.login` + code2session 需要后端，不值得为它引入云函数。存档走本地（wx 存储适配层透明），`TapTapBootstrap` / `LoginTapRowBuilder` / `SaveSystem` 里的 TapTapGuestId 逻辑随 TapTap 剥离一并处理。
- **广告**：DirichletMediation（AdMob/TapADN 聚合）→ 微信激励视频 `wx.createRewardedVideoAd`。「广告送佣兵」等入口只对齐「看完/中途关闭」两种回调。
- **评价**：TapTapRatePopup 直接隐藏/删除（小游戏靠分享裂变，不靠评分）。
- **分享**：ShareService → `wx.shareAppMessage`（主动分享 + 右上角菜单卡片）。
- **埋点**：GameAnalytics 里的 TapTap 依赖 → 微信小游戏数据助手（后台自带，代码可先空实现）。
- **TapTap SDK 剥离**：manifest.json 移除 taptap 包 + scoped registries，Assets/TapSDK、Assets/Scripts 里的 TapTap 引用点清理（放手做，Android 包不再是约束）。

### 2.2 必须特殊处理的点
- **VideoPlayer（3 处）**：OpeningIntroOverlay / TutorialDirector.Town / LoginIntroSplash。小游戏 WebGL 下 VideoPlayer 不工作。方案三选一：
  a. 用微信 `<video>` 标签方案（适配层有 video 插件，改动最小）；
  b. 开场视频改成图片序列+音频（最稳，还能省 15MB）；
  c. 小游戏端直接跳过开场视频（最快上线）。
  **建议先用 c 上线，a/b 二期再补。**
- **Application.platform 判断**：SafeAreaFitter、ShareService 里有平台判断，要补 `RuntimePlatform.WeChatMiniGame`（团结引擎有对应枚举）分支。小游戏的刘海避让逻辑和手机端不同，验证一下现有 SafeAreaFitter 行为。
- **外部依赖**：TapTap SDK、External Dependency Manager 要在小游戏构建里整体排除（编辑器脚本里按 BuildTarget 剔除程序集/目录），Android 包不受影响。

### 2.3 不用改的
- SaveSystem 的文件/PlayerPrefs 读写（适配层透明）；版本清档逻辑保留。
- UI 全套（UICanvasSetup/SafeAreaFitter/UiLayoutStretch 那套规矩照旧）。
- 战斗、RPG 玩法逻辑、Newtonsoft 序列化。

## 二点五、资源引用分析结果（2026-11-01 实测，工具 Tools/ScanAssetRefs.py）

> 入口 = BuildSettings 场景（Boot/Town/Battle）+ 全部 Resources 目录 + GUID 依赖闭包。**只出报告，未动任何资源**。明细：`Logs/ScanAssetRefs_report.md` + `Logs/ScanAssetRefs_unused_detail.txt`。

| 结论 | 数据 |
|---|---|
| 实际打包可达 | **278MB**（2101 个文件） |
| 候选零引用 | **1.3GB**（5568 个文件） |
| Art/Effects | 1.2GB 里只有 **17.3MB** 可达，**3651 个文件 1.2GB 候选零引用**（Flipbook VFX 大贴图 20MB/个、Pixel Craft WAV 音效 5~8MB/个、Demo 场景） |
| Art/UI | 56.2MB 全部候选零引用（疑似旧版备份，Resources/UI 才是运行时用的） |
| Art/城镇 | 4.2MB 候选零引用 |
| SPUM/Core + Sample | ~3MB 候选零引用（插件示例） |
| Resources/Audio | 43.9MB 全部进包 → 转码目标 8~10MB |

**裁剪顺序（确认后执行，只挪不删）**：
1. Art/Effects 整目录搬家备份（保留可达的 17.3MB——明细里已标出）；
2. Art/UI 人工抽查后搬家（先确认不是「备用图库」）；
3. SPUM 示例、Demo 目录搬家；
4. 音频转码（Resources/Audio 43.9MB → mp3 96~128kbps 单声道）。

预期效果：源资源从 1.7GB → **~350MB**；配合贴图 ASTC 压缩，构建数据包有望压进 **60~100MB**。

## 三、包体与资源优化（工作量最大的部分）

### 3.1 分级瘦身策略（按见效快慢排序）

**第一刀：音频转码（预计省 100MB+，几乎零风险）**
- Resources/Audio 45MB + Art/Effects 里实际用到的 WAV，全部转 mp3（SFX 96~128kbps，BGM 128kbps，单声道采样率降 44.1k→可试 32k）。
- Unity 导入器统一设置：Force To Mono + 合理 Compression。
- 验收：工程内 grep 不到 >1MB 的音频文件。

**第二刀：Effects 大扫除（预计省数百 MB，需要引用分析）**
- Art/Effects 1.27GB 里 Pixel Craft VFX URP、Epic Toon FX、Flipbook VFX 等是整套商店包，实际被场景/预制体引用的可能只是一小部分。
- 做法：写一个引用分析脚本（从 Scenes + 预制体 + Resources 出发做依赖闭包），列出**零引用**的目录清单报你确认后移出工程（不删，挪到备份区）。
- 验收：Editor 下工程无 Missing 引用；包体报告（Editor.log 或 Build Report）体积下降。

**第三刀：贴图压缩与图集**
- 全部 UI 贴图设 ASTC（小游戏端 iOS/安卓都支持 ASTC，安卓低端机回退 ETC2 可选）。
- Icons/Art 里能合图的合 SpriteAtlas，压 DrawCall。
- 像素图勾 Point + 无 mipmap 的按需保留。
- 验收：Build Report 里 Texture 占比降到合理值（2D 游戏一般 ≤ 总资源一半）。

**第四刀：首包裁剪 + 分包/CDN 结构**
- 现在全部 Resources.Load 意味着这些资源默认全进包。团结引擎小游戏构建支持把 Resources 数据文件放 CDN（数据文件不走 4MB 限制），**但要先实测团结的拆包粒度**——如果数据文件只能整包下载，得把非启动必需资源从 Resources 挪到 AssetBundle/分包，按需加载。
- 启动必需：Boot UI（14MB 里挑）、核心配置、登录界面。目标首包+代码 ≤ 4MB 或走 CDN 数据文件方案。
- 这一步动加载结构，**风险最高，放最后做**，且要列出改动清单确认。

### 3.2 内存优化
- 竖屏 720×1280，贴图压缩到位后 2D 游戏内存可控。
- 重点盯：战斗特效（粒子贴图/序列帧）、VFX 目录 18MB 的运行时加载。
- 做法：加一个资源卸载巡检（场景切换时 `Resources.UnloadUnusedAssets`），避免常驻膨胀。

## 四、性能优化（上线前必做）

| 项 | 做法 |
|---|---|
| DrawCall | SpriteAtlas 合图 + Sprite/图集共享材质；跑 Profiler 看同屏 DC，目标 ≤ 100~150 |
| 粒子 | 战斗特效控制粒子数/overdraw；低端机档位可关部分粒子（小游戏用户设备跨度大） |
| 加载体验 | CDPCD 拆分下载 + loading 进度条；微信审核很看重首屏速度 |
| 帧率 | 目标 30fps 保底，低端机可锁 30 省电 |
| Shader | URP Shader 在 WebGL 下编译变体多，检查变体裁剪（ShaderVariantCollection），避免编译卡顿 |

## 五、平台接入清单（工程外的事，按「无后端无域名」拍板修订）

1. **注册小游戏账号**：微信公众平台注册「小游戏」类目，拿到 AppID。**主体：个人**（已拍板）——流量主开通门槛=**累计独立访客 UV ≥ 500**（官方现行口径）；个人主体禁虚拟支付，正好无内购无影响；**纯广告变现免版号**；软著：提审表单可先选「未取得」，不影响审核（被投诉侵权时才要求补交）——主人的软著已在版权中心流程中，下来后在后台补传，与上线互不等待。
2. **团结引擎构建**：Build Settings 切 WeChat MiniGame 目标，配 AppID（ProjectSettings 里已有 `m_SlimFeaturesWeixinMiniGame` 配置痕迹，说明团结目标摸过，正式配置一遍即可）。
3. **资源托管：不用备案域名**。用**微信云开发的静态网站托管/云存储**当 CDN——腾讯自家域名免 ICP 备案、自带加速、免费额度足够休闲游戏起步。把这个默认域名配到小游戏后台「downloadFile 合法域名」即可。
4. **登录：不做**。无内购无排行榜，纯本地存档（wx 存储自动云备份由适配层处理的话更好，不做强依赖）。
5. **支付：不做**（无内购，纯广告变现）。开通**流量主**（注册用户达标后）拿激励视频分成。
6. **审核材料**：休闲小游戏类目，准备软著等基础材料；提审前跑一遍真机全流程。
