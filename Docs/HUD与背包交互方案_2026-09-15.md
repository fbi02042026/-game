## 一、玩家第二条 → 雷击奥义充能

### 1.1 现成可用（不用新写攒能量的逻辑）

```csharp
HeroThunderUltimate.Instance.ChargeRatio   // 0~1 充能比例，直接可用
HeroThunderUltimate.Instance.IsReady       // 是否已满
HeroThunderUltimate.Instance.IsCasting     // 释放中（3~5 段落雷，约 0.9~1.4 秒）
```

充能规则（已实现）：击杀小怪 +1 / 精英 +3 / Boss +6；
需求点数 = `Clamp(10 + (章节-1)*4 + 关卡序*2, 10, MAX)`，即第一章首关 10 点。

### 1.2 ⚠️ 必须先决策：奥义总开关现在是关的

```csharp
GameConfig.THUNDER_ULT_ENABLED = false;   // GameConfig.cs:751
```

注释写的是「当前关，等后期装备技能再开」。**不打开这个开关，第二条会一直显示 0%**，看起来就像 bug。

三条路，需要你选：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 顺带打开开关** | `THUNDER_ULT_ENABLED = true`，第二条立刻有内容 | 奥义会真的开始自动落雷，且当前伤害倍率是「引导 2.8 / 第1章前期偏高」，可能改变战斗节奏与平衡 |
| **B. 保持关闭，UI 预留** | 开关关时第二条隐藏（玩家卡只留血条），打开后自动出现 | 现在看不到效果，等于白做，等开关打开才有价值 |
| **C. 改做别的用途** | 换成护盾 / 下一技能充能等 | 需要重新设计 |

> 推荐 **B**：先按 A 的方式把 UI 和接线做完，但用开关控制显隐。
> 这样开关一开就有表现，且不会现在就打乱平衡。

### 1.3 实现步骤

1. `CharacterSlotUI` 新增 `SetUltCharge(float ratio, bool ready, bool casting)`
   —— **不要复用 `SetEnergy`**，两者语义不同（能量 vs 奥义），复用后佣兵那边会串。
2. `BattleUI.CharacterBar` 玩家槽每帧（或节流）调用：
   ```csharp
   var ult = HeroThunderUltimate.Instance;
   playerSlot.SetUltCharge(ult != null ? ult.ChargeRatio : 0f,
                           ult != null && ult.IsReady,
                           ult != null && ult.IsCasting);
   ```
   关卡切换时 `RecalcNeed()` 已会刷新，无需额外处理。
3. 开关关闭 → `lanBarFill.gameObject.SetActive(false)`，不要留空条。
4. `ShowUnavailable()` / `ShowEmpty()` 里同步隐藏第二条。

### 1.4 表现建议

| 状态 | 表现 |
|---|---|
| 0 ~ 99% | 蓝紫色填充 + 文字 `7/10`（分子分母比百分比更直观） |
| 满（IsReady） | 条发光/描边脉动，文字改「雷击就绪」 |
| 释放中（IsCasting） | 条快速回落 + 短暂高亮，配合已有的落雷特效 |
| 开关关闭 | 整条隐藏 |

> 佣兵卡**保持现状**（显示技能能量），不要一起改成奥义——佣兵没有奥义。

## 二、被动技能拖拽排序（仅整理阶段）

### 2.1 好消息：轮子已经造好了

- `SkillOrderChip.cs`：完整拖拽组件（横向列表重排，用 `SetSiblingIndex` + LayoutGroup 自动回流，不跟手——比跟手漂移更稳，不会出现松手飘回原位的幽灵帧）
- `RunLoadout.MoveSkill(from, to)`：写回接口，注释明确「槽序即自动释放优先级，越靠前越优先」

缺的只是：**没挂到底部 4 技槽上**，以及**没有整理阶段的开关**。

### 2.2 改动点（3 处，都很小）

1. `SkillOrderChip` 加一个开关字段：
   ```csharp
   public bool DragEnabled = true;   // false 时 Begin/Drag 直接 return
   ```
   目前组件没有任何启用判断，必须加，否则战斗中也能拖。
2. 底部 4 技槽（`SkillBar/icon底0~3`）在 `BindRunSkillSlots` 里挂上 `SkillOrderChip`，
   并**按实际槽宽设置 `SlotStep`**（chip 宽 + spacing，算错会导致拖到错误位置）。
3. 拖拽结束时按 `SiblingIndex` 变化写回：
   ```csharp
   // 只在 BattleLootMode.Active 时允许拖
   chip.DragEnabled = BattleLootMode.Active;
   // OnEndDrag 后：
   RunLoadout.MoveSkill(fromIndex, toIndex);
   // 然后必须重建技能 + 刷新 HUD（MoveSkill 注释明确要求）
   ```

### 2.3 交互细节

- **进入整理阶段时**统一置 `DragEnabled = true`，退出时置 false（`BattleLootMode.Changed` 事件可订阅）。
- 拖动时给一点视觉反馈（半透明 / 抬高 / 描边），否则玩家不知道能不能拖。
- 首次进入整理阶段时给一次轻提示（如「拖动技能可调整释放顺序」），因为顺序影响自动释放优先级，不提示玩家不会知道。
- 排序后**立即刷新 4 个技槽**，让玩家看到新顺序已生效。

### 2.4 风险

- `BattleBackpackItemDrag` 也是在整理阶段生效的拖拽——但它在**背包格子区**，技槽在**底部条**，区域不重叠，**不冲突**。
- 顺序改变会真的改变自动释放先后（`PlayerSkillPassive` 明写「多个技能同时就绪取最靠前的」），所以**必须让玩家意识到这个改动有实际影响**，不能做成纯装饰。

## 三、道具系统 + 使用 / 丢弃（全新系统）

### 3.1 现状：从零开始

背包只有装备，没有任何道具/消耗品。要做「使用/丢弃」必须先建这套东西：

配置表 → 掉落来源 → 背包数据 → 格子渲染 → 交互 UI → 使用效果。

### 3.2 数据层：新增 `item_defs.csv`

建议字段（`Assets/Data/Source/Tables/`，写完要 Cook 成 `.bytes`）：

| 字段 | 说明 |
|---|---|
| `id` | 唯一 id |
| `name` | 道具名（**选中态要显示，必须有**） |
| `icon` | 图标资源路径 |
| `type` | `Consumable` 消耗品 / `Material` 材料 / `Quest` 任务道具 |
| `stackMax` | 堆叠上限（1 = 不可堆叠） |
| `useEffect` | 使用效果，如 `heal_hp:30` / `buff_atk:20:15` |
| `useTarget` | `self` / `ally` / `enemy`（决定能不能在战斗中用） |
| `canUseInBattle` | 战斗中是否可用 |
| `canDrop` | 是否允许丢弃（任务道具应为 false） |
| `desc` | 说明文字 |
| `rarity` | 稀有度（决定掉落与显示配色） |

### 3.3 背包数据改造（改动最小的做法）

`BackpackItem` 现在只有 `equip` 字段。建议**加字段而不是重构**：

```csharp
public class BackpackItem
{
    public EquipInstance equip;   // 原有
    public ItemInstance item;     // 新增：道具
    public bool IsItem => item != null;
    public int x, y, width, height;
}
```

好处：现有装备逻辑（`FindEmptyPosition` / `OccupyGrid` / 自动分解）完全不动。
道具固定 `1×1`，复用同一套格子占用机制即可。

**混排还是分页？** 两种都可以，看你想要的手感：

- **混排**（道具和装备挤在同一个 4×3 里）：统一、省事，但装备本来就占多格，12 格会很快塞满。
- **独立分页**（背包面板加「装备 / 道具」切换）：互不抢空间，道具可以做小图标 + 数量角标，更适合以后加更多道具类型。

> 推荐**独立分页**：12 格给装备都不一定够，混排会让「背包空间不足」更频繁。

### 3.4 选中态交互（你明确要求的部分）

流程：

```
点击道具 icon
  → 该格进入选中态（描边高亮）
  → 在 icon 旁弹出操作浮层：
       ┌──────────────┐
       │ 治疗药水        │  ← 道具名（必须有）
       │ 恢复 30 点生命  │  ← 说明
       │ [使用] [丢弃]  │  ← 两个按钮
       │            [×] │  ← 关闭按钮
       └──────────────┘
  → 点击「使用」：二次确认？→ 执行效果 → 关闭浮层 → 刷新背包
  → 点击「丢弃」：二次确认「确定丢弃治疗药水 ×1？」→ 移除 → 关闭
  → 点击浮层以外任意位置 / 点「×」：取消选中，浮层消失
```

要点：

1. **道具名一定要显示**——你说得对，光看图标判断不了是什么。浮层标题用 `item_defs.name`，堆叠时显示 `治疗药水 ×3`。
2. **点别处取消**：在全屏加一个透明的 `DismissPanel`（`Image` 全透明 + 接收射线），点击时关闭浮层并取消选中。这是 UGUI 的标准做法。
3. **关闭按钮**：右上角 `×`，与「点别处取消」走同一个 `Dismiss()`。
4. **二次确认**：丢弃建议强制确认（不可撤销）；使用可配置（消耗品用了就没了，但战斗中使用通常不希望被打断，建议不确认）。
5. **不可用的道具要灰掉**：`canUseInBattle=false` 的道具在战斗中「使用」按钮置灰；`canDrop=false` 的任务道具不显示「丢弃」按钮（而不是点了报错）。

### 3.5 与装备点击的分工（避免冲突）

现在是「点装备 = 穿戴/卸下」。道具不能沿用，否则点一下就用了，没有确认机会。

| 类型 | 点击行为 |
|---|---|
| 装备 | 保持现状：点击直接穿戴/卸下（拖拽换位） |
| 道具 | 点击 = **选中**并弹出操作浮层，不立即使用 |

两种行为靠 `BackpackItem.IsItem` 分流，在同一套点击处理里分支即可。

## 四、顺带发现的缺口（要不要一起做）

| # | 缺口 | 现状 | 建议 |
|---|---|---|---|
| 1 | **已穿戴的装备脱不下来** | `UnequipItem()` 有实现，但 5 个快捷槽只能看不能点 | 给快捷槽加点击 → 卸下；或点槽位时弹出该件装备的详情 + 「卸下」按钮 |
| 2 | **换装没有属性对比** | 看不到「换这件 攻 +12 / 防 -3」 | 穿戴前弹对比浮层，列出变化的属性行（绿升红降） |

> 其中 **#1 是真 bug 级缺口**：装备穿上去就下不来，只能靠穿别的顶掉。建议优先级提到最高。
