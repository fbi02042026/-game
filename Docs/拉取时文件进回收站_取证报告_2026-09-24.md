# 「每次 pull 都删一堆文件」取证报告

时间：2026-09-24 21:20–21:30　｜　仓库：`E:\xiangsumaoxian`　｜　事件：pull `89972353 → 9a6537ff`（774 文件变更）

结论分两层，**都已用实验证实**，区分「已坐实」与「待取证」，不做无据推断。

---

## 一、已坐实的事实

### 事实 1：E 盘上「任何删除」都会进回收站，C 盘不会

对照实验（同一段 node 代码，直接调 Win32 删除 API，**不经过 shell / shim / git**）：

| 实验 | 操作 | 结果 |
|---|---|---|
| A | `fs.unlinkSync('E:\...\_tmp_evidence_E.txt')` | **进了回收站**（21:28:23 有记录） |
| B | `fs.unlinkSync('C:\Users\Admin\AppData\Local\Temp\_tmp_evidence_C.txt')` | **没进回收站**（C 盘回收站 0 条） |

→ 说明这是 **E 盘卷级**的删除重定向行为，与 git 无关、与 WorkBuddy 的 `rm` shim 也无关（node 根本不走 shim）。
附带证据：21:24:19 用 node 删掉的 7 个 `Tools/_tmp_*` 临时文件，全部出现在 E 盘回收站。

### 事实 2：git 替换文件，在这台机器上就表现为「进回收站」

实验 C：`git checkout HEAD -- Assets/Resources/UI/TalentIcons.meta`
→ 回收站 21:28:23 出现 `E:\xiangsumaoxian\Assets\Resources\UI\TalentIcons.meta`。

git 更新工作区 = **删旧文件 + 写新文件**，这是 git 的固有行为，任何机器都发生；只是别的机器删完就真没了，这台机器被送进回收站、留下了痕迹。

### 事实 3：本次 1876 条删除记录，逐条对账后「没有一个 git 不该删的文件」

用 `git ls-files`（15035 个跟踪文件）逐一比对回收站记录：

| 类别 | 条数 | 说明 |
|---|---|---|
| **git 跟踪文件** | **1829** | git 更新时的正常替换（旧版本被丢弃） |
| `.git/*.lock` 等锁文件 | 9 | git 自己用完即删（`index.lock` / `maintenance.lock` / `packed-refs.lock`…） |
| 我本次自建的 `Tools/_tmp_*` | 7 | 骚货自己删的 |
| 目录路径 / 被截断的文件名 | 31 | 形如 `Assets\Art\UI\Boot`、`…\设置\`、`冒险_0001s_0005_`，是 git 处理目录移动与重命名时产生的记录，不是真实文件删除 |

→ **不存在「外部进程偷删项目文件」**。

### 事实 4：删除记录的时间戳，与每一步操作严格一一对应

| 时间 | 删除记录 | 对应动作 |
|---|---|---|
| 21:20:23–25 | 20 条 `.meta` | 骚货为解除 merge 阻塞而 `git checkout HEAD --`（挡路的 CRLF 假改动文件） |
| 21:20:32–34 | 大批（约 776） | **pull 本身**：git 更新 774 个文件 |
| 21:21–21:22 | 再一批 | **post-merge 钩子**执行 `git checkout-index -f -a` |
| 21:22:39–40 | 12 条 | 当前 `git status` 里那 12 个 ` M`（CRLF 假改动）被重写 |

工作区文件写入时间统计（15035 个跟踪文件）：

```
21:21  → 650 个文件被写
21:22  → 1276 个文件被写
当前缺失：0
```

→ 证实钩子确实在 pull 之后**又重写了约 1900 个文件**（远超 git 更新的 776 个），这才是「删得多」的主因。

### 事实 5：重写本身不会造成丢失

实验 D：单独执行与钩子完全相同的 `git checkout-index -f -a`
→ 耗时 **2.1 秒**，结束后 `git diff --diff-filter=D` = **0**。

## 二、因果链（已证实部分）

```
pull → git 更新 776 个文件（删旧写新）
        ↓ 旧文件被 E 盘机制送进回收站（事实 1、2）
post-merge 钩子自检 → 报告「1152 个文件消失」
        ↓ 触发安全网
git checkout-index -f -a → 强制重写所有 stat 不一致的文件
        ↓ 又产生约 1900 次「删旧写新」→ 又一批进回收站（事实 4）
恢复完成，最终缺失 0
```

**「删东西」的真正放大器是我们自己装的 post-merge 钩子**（`.git/hooks/post-merge` 第 23–39 行），不是 git。
git 那边只贡献 776 条；钩子那轮才是大头。

## 三、尚未坐实的一点（明确标注，不猜）

**钩子为什么会报告 1152 个文件「消失」？** 数字大于 git 更新量，说明那一刻确实有一批文件在工作区查不到。

- 实验 D 证明「重写动作本身」不会造成缺失（0 缺失）→ 排除钩子自己造成的可能。
- 进程列表里查到常驻程序：**`360tray.exe`（360 安全卫士）、`LiveUpdate360.exe`**，以及 Windows Defender（`MsMpEng.exe`）。
  实时扫描在 git 写入后短暂占用/延迟落盘，是最可疑的解释。
- **但这条没有拿到直接物证**：`fltmc filters`（查文件系统过滤驱动）和 `reg query`（查已安装软件）都被环境安全策略拦截（Program Blacklist），无法进一步取证。
- 因此这里**只列为高度可疑，不下定论**。

### 取证办法（下次 pull 就能拿到实锤名单）

给 `.git/hooks/post-merge` 的检测处加两行，把消失文件的名单落盘：

```sh
if [ "$DEL" -gt 20 ]; then
    git diff --name-only --diff-filter=D > .git/last_pull_missing.txt 2>&1   # ← 新增
    echo "$(date) DEL=$DEL" >> .git/last_pull_missing.log                     # ← 新增
    ...
```

有了名单就能判断：是集中在某几个目录（→ 扫描/占用），还是随机散布（→ 删除重定向的时序问题）。

## 四、结论与建议

1. **不必慌**：所有「删除」都是旧版本文件进回收站，工作区最终 **0 缺失**，git 状态干净（12 个 ` M` 全是 CRLF 假改动，`--numstat` 为空）。
2. **想让记录变少**：把钩子阈值从 20 调高、或让它先 `sleep 3` 再检测（避开扫描瞬时窗口），能显著减少无谓的二次重写。改不改由主人拍板。
3. **想根治**：需要确认/暂停 360 安全卫士的文件防护与 Defender 实时扫描后再复现一次 pull，对比是否还有成片消失。
4. 拉取后**记得重启团结编辑器**重新导入（`.meta` 被批量重写过，不重启可能缓存错位白框）。
