> **日期**：2026-09-26 ｜ **范围**：只读扫描 `Assets/Scripts`（346 个 .cs）+ 8–9 月提交历史。**本次不改任何代码。**

> **先回答指标问题**：本方案直接服务**留存**——减少"改好的问题过几天又出现"，就是减少玩家反复遇到同一个卡点/同一个错误表现而流失；间接服务**在线时长**——结构清楚后加章节/职业/玩法的速度从"周"降到"天"，内容更新频率上去，长期留存才起得来。

## 1. 一句话结论

**Bug 复发不是因为没修好，而是因为同一个东西有不止一个"能改它的地方"。** 你把 A 处改对了，B 处（旧入口 / 兜底回退 / 单例残留 / 预制体重建）在某个条件下又把旧值写回去，表现出来就是"过几天又复发了"。

模块化在这件事上的价值只有一个：**让每份状态只有一个写入者**。不是为了代码好看。

## 2. 复发的五个根因（按证据强弱排序）

### 根因 ① 同一语义，多套资源 + 多个入口 —— 改一处，旧入口把效果拉回去 ★最痛

**活标本：职业图标。注释里就写着这是第二次修。**

- `Systems/MercHireSession.cs:185` 顶部注释：「★★★ 三套『职业图标』的口径，别再互相搞混（2026-09-26 主人反馈「总和玩家职业icon搞混」）★★★」
- `UI/BattleUI.CharacterBar.cs:91-92`：「2026-09-26：去掉『取不到回退职业立绘头像』——那正是主人说的『总和玩家职业icon搞混』」

现状是**一个"职业图标"概念，三套资源、四个加载函数、分布在 4 个文件**：

| 用途 | 资源目录 | 入口函数 | 所在文件 |
|---|---|---|---|
| 佣兵/战斗 HUD 四分类徽标 | `Icons/职业icon/{物攻,法术,防御,恢复}` | `MercHireSession.LoadMercJobBadge`（旧名 `LoadJobIcon`） | `Systems/MercHireSession.cs` |
| 玩家职业立绘头像（三选一卡面） | `Icons/Job/` | `PlayerJobDefs.TryLoadJobIcon` | `Config/PlayerJobDefs.cs` |
| 玩家职业 icon（6 张） | `Icons/玩家职业icon/` | `PlayerJobDefs.TryLoadCombatBadgeIcon` | `Config/PlayerJobDefs.cs` |
| UI 补件（缺 Image 就运行时新建） | — | `BattleUI.WidgetFactory.EnsureJobIcon` | `UI/BattleUI.WidgetFactory.cs:535` |

同一个 `SetJobIcon` 被 **3 个文件、8 处**调用（`BattleUI.CharacterBar.cs` 94/135/191/213/237、`CharacterSlotUI.cs` 736/770、`BattleUI.Binding.cs` 408）。
**只要还有一处调旧函数，旧图就会回来。**

这类"同义多入口"在代码里不止图标一处，它是复发的头号来源。

### 根因 ② 静默兜底：取不到就回退到"修之前的行为" ★最隐蔽（数据已更正，见下）

> ⚠ **2026-09-26 23:30 更正**：初版写「`??` 999 处、`Monster.cs` 485 处」是**错的**，
> 当时把**注释里的"兜底/回退"字样也数进去了**。剔除注释与字符串字面量后逐级收敛：

| 口径 | 数量 | 说明 |
|---|---|---|
| 初版（含注释） | 999 | ❌ 作废，注释里的"兜底"二字被计入 |
| 剔除注释后的 `??` | 512 | 仍偏大 |
| 再剔除 `??= new List<>()` 懒初始化 | 380 | 绝大多数集中在 **UI 层** |
| 再剔除"按多个候选名字找节点"的容错查找 | **35** | ✅ **真正的"取不到就换另一套资源"** |

**结论修正**：`Monster.cs` 实际只有 **18 处** `??`（不是 485），它没有"兜底泛滥"问题；
`SaveData.cs` 的 79 处全是 `??= new List<>()` 懒初始化（JsonUtility 反序列化必需，**正常且必要**）。
真正值得盯的是那 **35 处"跨资源回退"**（如 `BattleUI.CharacterBar.cs:207` 三套头像层层回退），
但其中过半是 `GetComponent<X>() ?? GetComponentInChildren<X>()` 这类**组件查找容错**，属有意设计、不该动。

对排期的影响：**Phase 7.2（给几百处兜底加日志）收益远低于初估，已降级**——
改成只做"可见性"（Guardrails 的 G4 扫描列出这 35 处），不再到处插日志。

**为什么这是复发的直接机制**：兜底值几乎总是"改之前那个行为"。一旦发生资源缺失、节点改名、加载时序晚了一帧、预制体重新导入——它就静默走回旧分支，而日志里什么都不打印，看起来就是"莫名其妙又坏了"。

### 根因 ③ 单例 + 跨场景残留 + 静态可变字段 —— "第一次好，第二次坏"

- **59 个** `public static Xxx Instance` 单例（含 `Unit/Hero.cs:10`、`Unit/HeroCostumeManager.cs:21`、`UI/*` 四十余个）
- **51 个文件**用了 `DontDestroyOnLoad`（69 次）
- **204 个** `public static` 可变字段（非 const/readonly），跨场景不重置

叠加 `Core/Singleton.cs:46,122`「找不到就 `FindObjectOfType`，再找不到就 new 一个」——**实例可能凭空产生，时序不确定**。
后果：同一段代码，第一次进战斗对的，第二次进战斗被上次残留状态覆盖。主观感受就是"一会儿好一会儿坏"。

### 根因 ④ 靠名字找节点 —— 预制体一动就断

- `GameObject.Find("GameRoot"/"Ground"/"Unit"/"SpawnPoint"/…)` **17 处**
- `FindObjectOfType<>` **30 处**
- 重灾区：`Core/AutoGameInitializer.cs`（1168 行，12 处）、`Core/BattleViewportFit.cs`、`UI/TownSceneBootstrap.cs`

节点改名或预制体重建 → 找不到 → 走根因 ② 的兜底 → 表现"复发"。

### 根因 ⑤ 修复没有闸门 —— 修完被后续提交静默覆盖

提交历史里有实锤：

```
e3f176f7 fix(core): Singleton 构造期访问 isPlaying 抛 UnityException —— 重新应用 9-15 的修复
```

**同一个修复被应用了两次**，说明中间有提交把它冲掉了，而没人发现，直到再次抛异常。
项目目前没有任何"已修复项 = 断言"的机制，全靠人肉记忆。这是"复发"能成立的前提条件。

## 4. 目标架构（四条硬规则，不是画大图）

```
L3 表现层   UI（只读订阅，禁止回写领域数据）
              ↓ 只能通过事件/接口
L2 编排层   BattleManager（只留：本局状态机、胜负、能量、接线）
              ↓
L1 领域服务  EquipService / SkillService / MercService / WalletService / SaveService
              ↓
L0 数据真源  Cook 表 > SO > GameConfig（只读常量）
```

依赖只允许 **L3→L2→L1→L0 单向**。禁止反向调用、禁止跨层直接抓单例、禁止 UI 直接写存档。

**四条防复发硬规则（比分层更重要，这是本方案的核心）**

| # | 规则 | 具体做法 | 治哪个根因 |
|---|---|---|---|
| **R1** | **单一写入者** | 每份状态/外观只有**一个**写入函数。旧同名入口标 `[Obsolete]` 并转调新入口，Editor 下调用旧入口打 Error。 | ① |
| **R2** | **禁止静默兜底** | 取不到资源/节点 → 打 `Debug.LogError`（Editor）/ Warning（真机）+ 显示占位灰块；**绝不回退成旧行为的默认值**。 | ② |
| **R3** | **单例不得自动 new** | `Singleton<T>` 找不到实例就报错，不再凭空 new；跨场景状态集中到一个 `RunSession`，进战斗显式 Reset。 | ③④ |
| **R4** | **修复即断言** | 每修一个复发 bug，在 `Tools/Guardrails.py` 加一条检查；提交前必跑，跑了才准提交。 | ⑤ |

R4 是让"复发"从机制上不可能的那一环：**修过的东西被改回去，脚本会当场叫。**

##### ⚠ 写完自检抓到的一个 bug（记下来，同款代码还会再写）

第一版 `Get<T>()` 里我写的是：

```csharp
var uo = s as UnityEngine.Object;
if (uo != null) { if (uo == null) { /* 剔除 */ } return uo as T; }
```

**这是错的**：`uo != null` 用的也是 Unity 的 `==` 重载 —— 已销毁对象会让**外层判断直接为 false**，
于是跳过剔除、把僵尸引用当成有效服务返回。一个专门用来防「跨场景残留」的类，自己就带着这个残留 bug。

正确写法是**两层判空，两个含义**：

```csharp
if (s is UnityEngine.Object uo)   // 类型检查，不受 == 重载影响：它是不是引擎对象
{
    if (uo == null) { /* Unity 重载：已销毁 → 剔除 */ }
    return uo as T;
}
return s as T;                     // 非引擎对象（纯 C# 服务）走这条
```

教训：**Unity 里凡是 `UnityEngine.Object` 的判空，都要分清「引用存不存在」和「对象有没有被销毁」**，
用 `is` / `ReferenceEquals` 判前者，用 `== null` 判后者。
