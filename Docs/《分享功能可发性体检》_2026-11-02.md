**不可发。** 微信小游戏端「立即分享」是个空转按钮：点一下什么都不弹，直接白送 100 钻；

TapTap/安卓端（`UNITY_ANDROID && !UNITY_EDITOR`）的分享链路是**通的**，本次体检不涉及改动。

## 三、问题清单

### P0-1 微信端分享空转，点一下白送钻

- **位置**：`Assets/Scripts/Systems/ShareService.cs:136-174`（`LaunchSystemShare`）
  - 第 138 行 `#if UNITY_ANDROID && !UNITY_EDITOR` → Intent + `ShareFileProvider.java`（安卓通）
  - 第 170-172 行 `#else` → 只 `Debug.Log("非安卓真机（Editor 测试口径）：视为分享面板唤起成功")` 然后 `return true`
- **现象**：微信端点「立即分享」→ 无任何界面 → `TryShareAndReward` 认为唤起成功（第 57 行）→
  记 `#share_launch`（第 60 行）→ 写日键 + 发 100 钻（第 75-76 行）→ toast「分享成功：钻石 +100」
- **影响**：这不是分享功能，是无成本领钻入口。每日一次 × 全量玩家 = 白送经济产出，且传播量为零。
- **修法**：加 `#if UNITY_WECHATMINIGAME` 分支走微信桥（见 P0-2），安卓分支原样保留；
  微信分支返回真实成败（`wx.shareAppMessage` 调起失败 → 不发奖）。
- **验收**：微信开发者工具点「立即分享」→ 真的弹出转发选择界面；取消转发按口径处理（见第四节）。

### P0-2 微信转发桥完全缺失

- **位置**：需新建 `Assets/Plugins/WeChatShare.jslib` + `Assets/Scripts/Platform/WeChatShare.cs`
- **范式**：直接照 `WeChatAd.jslib` / `WeChatAd.cs`（2026-11-02 已跑通同一套模式）
  - C#：`#if UNITY_WECHATMINIGAME` + `[DllImport("__Internal")]` + `MonoPInvokeCallback` + `Marshal.GetFunctionPointerForDelegate`
  - jslib：`mergeInto(LibraryManager.library, {...})`，内部调微信运行时全局 `wx`
- **接口**（均为微信官方 API，非编造）：
  - 主动转发：`wx.shareAppMessage({ title, imageUrl, query })` —— **必须在用户点击手势内同步调用**
  - 菜单控制：`wx.showShareMenu({ withShareTicket: true })`
  - 被动转发：`wx.onShareAppMessage(function(){ return { title, imageUrl, query }; })`
- **验收**：真机点分享能拉起通讯录选择页；右上角菜单「转发」出去是自定义卡片（标题+图），不是微信默认内容。

### P0-3 分享封面图比例不对

- **位置**：`ShareService.ShareImageResPath = "UI/Art/分享/分享竖"`（第 34 行）
- **事实**：微信转发卡片显示比例固定 **5:4**（官方文档：`imageUrl` "显示图片长宽比是 5:4"），
  支持代码包内相对路径 / 本地路径 / 网络图，**不支持 base64**。
- **现状**：竖图 940×1672（0.56:1）会被横切掉上下大半，横图 1672×941（1.78:1）会被裁左右。
- **修法**：另出 1 张 **1000×800（5:4）** 封面图放 `Assets/Resources/UI/Art/分享/`，
  微信分支直接传代码包相对路径，**不要**走 `EncodeToJPG` + `persistentDataPath` + FileProvider（那是安卓专用链路）。
- **验收**：转发卡片上封面完整不变形、无黑边裁切。

### P1-1 埋点在微信端看不到

- **位置**：`GameAnalytics.cs:281-319`（4 个分享事件）；`WeChatAnalyticsBridge.cs:38` 自述无 jslib
- **现象**：`GameAnalytics.Log` 走 TapDB（`TAPSDK_ENABLED`），微信构建不上报；微信后台自定义事件 `wx.reportEvent` 未接。
- **影响**：不影响玩家侧功能，但上线后**看不到分享量/分享转化**，等于瞎飞。
- **修法**：给 `WeChatAnalyticsBridge` 补一个 `WeChatAnalytics.jslib`（`wx.reportEvent(eventId, obj)`），
  或至少先接分享 4 个事件。
- **附带**：`ShareService.cs:55` 的 `ReportShareClick("battle_report", sceneTag)` 里 `share_type` 硬编码 `battle_report`，
  微信端语义不准（不是战报），建议改 `system_share` 或按平台取值。

### P2-1 入口只有一个

- **影响**：不打关的玩家永远看不到分享入口；微信端更依赖日常传播。

## 四、合规专章：为什么推荐微信端不发钻

### 4.1 规范原文（微信《小程序/小游戏平台运营规范》2.5.1 滥用分享行为）

> 不得强制用户分享、暗示用户分享，不得**利益诱导分享**至朋友圈，……其中"利益"包括但不限于：
> 现金奖励、实物奖品、**虚拟奖品（红包、优惠券、代金券、积分、话费、流量、信息等）**
> 4. **无深度互动诱导分享**：以分享后无需互动或无需深度互动即可获得利益的方式诱导分享至群或好友，
>    "深度互动"是指被分享者理解被分享内容并主动参与活动或业务流程
> 6. 分享收益存在概率性 ……
> **处理规则**：一经发现将根据违规程度，对小程序**限制活动页面、限制分享能力**……直至**下架封号**处理。

配套 2.5.28：利诱分享次数过多会触发**频率限制**（新增分享页面被限制访问）。

### 4.2 本项目命中情况

| 位置 | 文案 | 判定 |
|---|---|---|
| `分享.prefab` Info 文本 | 「分享成功领 100 钻石 / 每日一次」 | 命中：虚拟奖品（钻石）直接换分享 |
| `BattleResultScreen.cs:460` | 「分享获得100钻石，每日一次」 | 命中 |
| `BattleResultScreen.cs:475` `BuildShareRewardRow` | 分享按钮下「+100钻石」图标行 | 命中，且属于"暗示/强调利益" |
| 发奖时机 | 点分享 → 调起转发界面 → **立即发钻**（不等好友互动） | 命中第 4 项「无深度互动」 |

### 4.3 三种方案对比

| 方案 | 改动量 | 审核风险 | 传播效果 | 变现 |
|---|---|---|---|---|
| **A. 微信端不发钻（推荐）** | 小：三处文案 + `TryShareAndReward` 微信分支不发奖 | 归零 | 靠战报/海报内容驱动，量会降但真实 | 每日福利改挂激励视频（合规且更赚） |
| B. 保留发钻照提审 | 中：接桥 + 保留奖励 | 高：拒审 / 限制分享能力 / 累犯影响账号权重 | 有量但可能随时被掐 | 无 |
| C. 分享后好友进入才发奖 | 大：query 归因 + 新用户标记 + 发奖延迟 | 中：形式合规，但"深度互动"仍由平台判定 | 需好友真进来，量低 | 无 |

### 4.4 推荐 A 的四条理由

1. **处罚代价远大于收益**：钻石是无限增发的虚拟品，送 100 钻成本≈0；但「限制分享能力」等于切断小游戏最主要的自然流量入口，
   一次处罚的损失是永久性的。用几乎为零的收益去赌唯一的增长通道，不划算。
2. **这是明文禁止、不是灰色地带**：规范把"虚拟奖品"直接写进"利益"定义里，且第 4 项精确描述了本项目的形态
   （分享完不需要好友做任何事就发奖）。审核员看到「分享成功领 100 钻石」是**一眼命中**，不存在解释空间。
3. **微信已经给了合规的替代品**：激励视频是官方明确开放、且是 IAA 变现主路径。项目 `WeChatAd.cs` + `WeChatAd.jslib`
   已经接好，只差 `WeChatMiniGameConfig.RewardedAdUnitId` 一个值（`GameConfig.Progression.cs:103` `ADS_ENABLED` 目前 false）。
   把「每天 100 钻」从分享挪到看视频：**玩家照样拿钻、项目反而赚钱、审核零风险**。
4. **改动成本极低**：A 方案是删三处文案 + 一个分支判断，半天内能收；B 方案要接全套桥 + 出图 + 真机验，
   然后可能被打回再改一遍再排队审（微信备案本身 13~37 工作日），时间成本高一个数量级。

### 4.5 如果坚持要保留分享激励

唯一相对安全的形式是 C（分享→好友进入游戏→才发奖），且必须：
- 分享 query 带可归因参数，好友首次进入时回传；
- 活动规则在界面显著位置完整说明（规范 2.5.1 第 5 项）；
- 奖励即时发放（第 7 项禁止"长期参与才可得"）；
- 不做概率性收益（第 6 项）。
