## 一、签名是什么？——不是"名字"，是"印章"

### 一句话

**签名 = 给 APK 盖一个只有你能盖的印章，证明"这个包是从我这出来的、中途没被人动过"。**

不是名字，不是账号，**和平台数量无关**。一个 keystore（印章文件）可以盖在所有平台的包上。

### 用生活比喻

想象你开了一家店，每次给客人发一份密封文件袋：

- **包名**（`com.PixelAdventure.RiftBlade`）= 文件袋上写的**收件地址**。全设备唯一，**定下不能改**。
- **签名** = 封口处压的**火漆印章**。系统拆包时会验章：
  - 章对得上 → 是同一个作者发的，允许**覆盖安装/升级**；
  - 章对不上 → 认定"这不是同一个作者的包"，**拒绝安装**。
- **keystore 文件** = 那枚**印章本身**（`.jks` 文件）。
- **密码** = 保险箱钥匙，保护这枚印章不被别人拿去用。

### 为什么签名不能换

安卓的规矩是：**同一个包名的应用，只有签名一致才允许"升级覆盖"。**

所以一旦你用某个签名发布了包，以后**必须一直用同一个签名**。换了会怎样：

| 场景 | 结果 |
|---|---|
| 玩家装过旧包，你换签名发新包 | 提示"应用签名不一致"，**装不上**，必须卸载重装（存档没了） |
| TapTap 传过旧包，你换签名传新包 | 平台可能判定为**新应用**，或者审核告警 |
| 你自己手机测试，debug 包换成正式包 | **覆盖安装会失败**，得先卸载 |

👉 所以女仆建议：**聚光灯这一次就把正式签名定下来，用一辈子。** 早定比晚定省事得多。

### 一个 keystore 服务所有平台吗？

**是。** keystore 是"你是你"的证明，不是"给某个平台的通行证"。

| 平台 | 要不要单独做签名 |
|---|---|
| TapTap（聚光灯/TapPlay） | 用同一个 keystore |
| 微信小游戏 | 走微信后台配置，另说（本项目不接） |
| Google Play | 用同一个 keystore（Google 另有"Play 应用签名"机制，会上传你的公钥） |
| 自己发 APK 给朋友 | 同一个 keystore |

**结论：只做一次，一个 `.jks` 文件 + 一组密码，全都够用。**

### 还有一件事：包名也不能改

顺便提醒（这条比签名更硬）：**包名 `com.PixelAdventure.RiftBlade` 绝对不能改。**
改了 = 平台认成全新应用，玩家存档、下载量、评价**全部清零**。现在这个值是对的，别动。

## 二、加密防拆包：能不能做？能，但"简单加密"有个关键前提

### 先认清现实：客户端加密拦不住专业的人

安卓 APK 本质是个 zip。专业破解者手里有 IL2CPP dump、内存抓取、动态调试等工具，
**只要密钥在客户端里，就一定能扒出来** —— 这不是本项目的技术问题，是所有手游的共同现状。

所以目标要定得实事求是：

| 目标 | 能不能达到 | 说明 |
|---|---|---|
| 挡住普通玩家改档（改金币/钻石） | ✅ 能 | 这是加密最大的实际价值 |
| 挡住用现成工具一键改档的人 | ✅ 能 | 提高门槛就够 |
| 挡住脚本小子改配表 | ✅ 大部分能 | 表加密后不能直接改 CSV |
| 挡住专业逆向 / 扒美术资源 | ❌ 挡不住 | 别为这个投入，性价比极低 |

**女仆的建议：做"够用"的加密，重点是改档防不住就白搭，逆向你拦不了。**

### 好消息：这家底子**已经建好了**，只差一个开关

女仆翻了代码，本项目**早就写好了完整的加密链路**，现在是关着的：

| 组件 | 文件 | 现状 |
|---|---|---|
| 加密算法 | `Assets/Scripts/Data/SecureCodec.cs` | ✅ 已写好：**AES-256-CBC + HMAC-SHA256**（工业级强度，不是"简单加密"） |
| 密钥派生 | `Assets/Scripts/Data/GameSecrets.cs` | ✅ 已写好：密钥**拆成两半在运行时混合**，磁盘上找不到明文密码 |
| 配置指纹 | `Assets/Scripts/Data/ConfigFingerprint.cs` | ✅ 已写好：怪物/装备/天赋/技能数值**逐条哈希校验**，改了表就报错 |
| 总开关 | `Assets/Scripts/Data/ContentProtection.cs:8` | ⚠️ `Enabled = false`（关着） |
| 存档读 | `SaveSystem.cs:27` | ✅ **已经兼容加密档**（先试解密，失败再当明文读） |
| 表加载 | `GameTableStore.cs:24` | ✅ **已经兼容加密表**（先试解密，失败再当明文读） |

**这意味着：加密不用从零写，只需要「开开关 + 重新导出表」两步。**

### 为什么现在不能直接打开（重要）

两条硬约束，主人得先知道：

**① 表必须重新 Cook 成加密格式，否则开开关 = 读不到表 = 游戏打不开**

现在的表是**明文**（`Resources/Data/Tables/*.bytes`）。如果只把 `ContentProtection.Enabled` 改成 `true` 而表还是明文：
《SaveSystem》会**正常**（它兼容明文），但表的加载路径要看 Cooker 的行为 —— 需要重新跑一次 Cook 生成加密表，
否则会出现整个数据表读不出来的风险。**这一步是"必须一起做"的，不能只改开关。**

**② 上次预制体被搞坏，很可能不是这一步的锅**

女仆翻了 `Docs/软著后开发备忘.md:126-156`，里面有明确记录：

> 上次白框的真凶是**我（上一任 AI）用脚本把 base64 guid 强改成 hex**，
> 导致编辑器下一轮导入把 meta 写回 base64 却**不改引用** → 引用悬空 → 预制体白框。
> 原文：**"先前判断是错的。之前认为 base64 guid = 被加密搞坏"，"这是造成白框的真正原因"。**

也就是说：**"加密搞坏预制体"这个归因，项目文档里已经自己纠正过了** ——
坏的是"手动改 meta guid 的脚本"，不是加密本身。

⚠️ **但女仆不敢替主人下结论说"加密绝对安全"。** 因为：

- 如果上次同时跑过**引擎资源加密**（`Assets/` 全量加密那种），那确实可能破坏资源引用；
- 女仆没有上次的完整操作记录，**只能报告存疑，不能保证**。

👉 所以女仆给主人一个**零风险的验证路径**（见下）。

### 三条路线（女仆推荐第 1 条）

#### 路线 1（推荐）：**只加密存档 + 配表，不碰引擎资源**

- **动什么**：`ContentProtection.Enabled = true` + 重新 Cook 数据表（`Resources/Data/Tables/*.bytes` 变加密）。
- **不动什么**：`Assets/` 里的预制体、贴图、场景、图标 —— **一个字节都不碰**。
- **效果**：普通玩家**改档改不动了**（金币/钻石/进度改了进游戏就报错）；配表也改不动了。
- **风险**：⚠️ 低。不涉及"资源引用链路"，**上次坏预制体那条路根本没走到**。
- **代价**：开开关后**旧存档自动兼容**（读得到），但**降级回来（改回 false）后旧加密档也读得到**（代码已兼容双向）。
- **需要验证**：开完必须真机跑一遍：进游戏 → 存档 → 杀进程 → 重进 → 看进度在不在。

#### 路线 2：**离线加密"防拆"加强版**（不推荐现在做）

团结引擎 `Player → Publishing Settings` 里有资源加密/属性加密选项（名称随版本变）。
**这就是最可能弄坏预制体的那一类**（要改资源的读取方式）。

- **建议**：**本轮不做**。聚光灯规则**禁止热更**、要求**断网可玩**，包体也不敏感。
  真要做，等项目定型、有充分时间验证时单独立项。

#### 路线 3：**代码混淆 / ProGuard**（另一种方向，和资源加密无关）

- 作用：把 Java 层类名方法名混淆成 `a.b.c`，让逆向的人看得费劲一点。
- 对本项目价值：**低**（游戏逻辑几乎全在 C# 侧，Java 层只有 Unity 启动壳）。
- 现状：`AndroidMinifyRelease = 0`（关着）。**保持关着**。

### 女仆建议的落地步骤（等主人点头才动）

| 步骤 | 动作 | 谁做 | 风险 |
|---|---|---|---|
| 1 | 先把**当前工程完整备份**（或确认能 `git restore`） | 女仆 | 零 |
| 2 | 先打一次**不开加密**的包，确认真机跑通（基准） | 主人 | 零 |
| 3 | `ContentProtection.Enabled = true` + 跑加密 Cook | 女仆（主人拍板后） | 低 |
| 4 | 再打一次包，**真机重点验收**：进游戏/存档/表/读档/重进 | 主人 | — |
| 5 | 全部通过 → 保留；有任何异常 → **一条命令回退**（改回 false + 重新 Cook 明文） | 女仆 | 零 |

**关键：第 2 步的"基准包"必须先有。** 有了基准，任何异常都能一眼看出是不是加密引起的。

## 三、回到主人那句「简单点也比没有强」

主人这句话，女仆**同意一半**：

- ✅ **同意**：不加密 = 谁都能改档，确实"太裸了"。
- ⚠️ **但要提醒**：现在这套**不是"简单加密"，是 AES-256 + HMAC**，强度已经是很够用的档位了，
  不需要另写"简单版"。开开关就能拿到完整强度 —— **没必要降级成弱加密**。
- ✅ 而且**架构还留了后手**：将来想更强，可以在 `GameSecrets` 里换密钥拆分方式、加设备绑定，
  不用动别的代码。

**所以女仆的建议是：路线 1，等你打完基准包之后，女仆给你开。**

## 四、签名 vs 加密 vs 包名 —— 一张表分清（易混）

| 名词 | 是什么 | 干什么用 | 会不会影响预制体 | 能不能改 |
|---|---|---|---|---|
| **包名** | `com.PixelAdventure.RiftBlade` | 应用的身份 ID | 不会 | ❌ 定死不能改 |
| **签名（keystore）** | `.jks` 文件 + 密码 | 证明是同一个作者，允许升级覆盖 | 不会 | ❌ 定下不能换 |
| **存档加密** | `SaveSystem` + `SecureCodec` | 防玩家改档 | 不会 | 可随时开关 |
| **配表加密** | `Tables/*.bytes` 加密 + 指纹 | 防改数值表 | 不会 | 可随时开关 |
| **引擎资源加密** | `Player → Publishing` 里那类 | 防扒美术资源 | ⚠️ **会**（可能） | 本轮不动 |
| **代码混淆** | ProGuard | 逆向看着费劲 | 不会 | 本轮不动 |
